# ThreadDock 두 기능 협업 실험 — 진행자 지침

이 문서는 **아직 실행하지 않은 실험 설계**다. 목적은 요구사항·설계·구현·검증의 연결, 공유 결정 전파, 세션 교체 후 재개, Monitor 관찰을 실제로 확인하는 것이다. 새 하네스 기능이나 성능 벤치마크를 만드는 작업이 아니다.

개발 참가자에게는 [문제지](harness-pilot-problem.md)만 전달한다. 아래 변경 카드와 판정표는 진행자가 해당 단계에 공개한다. 같은 대화에 전부 붙이지 않는다. 미리 노출됐다면 기록하고 ‘사전 정보 없이 재개했다’고 주장하지 않는다.

## 1. 실행 범위와 준비

사용자가 실험 실행을 요청한 뒤 시작한다. 현재 문서 작성은 실험용 저장소·Issue·세션 생성, 전역 설치 갱신, 장애 유발을 실행한 것이 아니다.

진행자는 다음 값을 한 번 채워 [기록 양식](harness-pilot-record.md)에 남긴다. 도구가 알아낼 수 있는 값은 직접 확인하고, 없는 실행 대상이나 승인 범위만 사용자에게 확인한다.

| 항목 | 선택·확인 방법 |
|---|---|
| 실험 대상 | 실제 업무와 분리한 실험용 GitHub 저장소 URL, 실제 기본 branch, 로컬 경로. 새 저장소 생성은 별도 허가가 있을 때만 수행 |
| Monitor | 사용할 ThreadDock ref와 정확한 build SHA. 현재 PR #106을 시험하려면 해당 변경을 포함한 버전이어야 함. 설정 오류 실험에는 실제로 분리된 시험 사용자/프로필과 설정 파일 경로 근거가 필요 |
| 지침 | 설치 원본 SHA, 실제로 읽힌 Skill·역할 경로, 프로젝트 override와 의도적인 차이 |
| 실행 환경 | Windows/Wails, 선택한 WSL 배포판·사용자, Python·Herdr·에이전트 도구 버전, 사용 모델/effort와 확인 가능한 runtime 근거 |
| GitHub | host, 실제 Project URL/필드 또는 Project 미사용. 권한이 없으면 Issue/PR 실험과 Project 미검증을 구분 |
| 범위 | 실험 branch/Issue/PR의 쓰기, 실험 전용 세션의 생성·인계·종료, 정확한 실험 binding 갱신. main 병합은 사람에게 남김 |

[설치 안내](../operator/global-agent-setup.md)로 source와 실제 적용 경로를 비교한다. 차이가 있으면 기록하고 설치 갱신은 기존 승인 범위에서만 한다. 저장소 지침의 존재나 파일 복사를 실제 Agent 적용 성공으로 세지 않는다. 대상 프로젝트에는 ThreadDock **개발용 root 설정**을 복사하지 않는다.

[현재 사용법](../operator/github-first-quickstart.md)과 [Herdr 지침](../../project-template/.agents/skills/herdr-local/SKILL.md)을 따른다. 관리 pane의 실제 ID를 사용하고, `HERDR_ENV` 주입·모델/권한 완화·기존 세션 강제 재시작을 하지 않는다. 과거 `parallel-pilot.md`의 폐기된 실행 엔진 명령은 사용하지 않는다.

실험 저장소에서 사용할 초기 commit을 고정한다. 저장소가 비어 있으면 승인된 범위에서 최초 README와 문제지를 준비할 수 있다. 실제 운영 설정·데이터·다른 프로젝트를 실험 대상으로 삼지 않는다. 이 문서의 실행 대상은 로컬 CLI 문제이며, 실제 Wails Monitor 검증은 별도 항목이다.

## 2. 최초 요청과 병렬 배정

아래 프롬프트의 빈칸을 실제 값으로 바꿔 Coordinator에게 전달한다. 변경 카드 R2는 아직 전달하지 않는다.

```text
실험 저장소: <실제 URL>
기준 branch / SHA: <실제 값>
작업 경로: <실제 절대 경로>
문제지: <harness-pilot-problem.md를 복사한 실제 경로>
Project: <실제 URL 또는 미사용>

문제지의 작업 현황 도구를 만들어 줘.
목록 조회 A와 진행 집계 B를 별도 기능으로 병렬 개발해.
기존 ThreadDock 지침을 사용하고 실제 환경의 모델·권한을 유지해.
실험 저장소의 Issue/branch/PR 작성과 실험 전용 Herdr 세션·연결 관리를 허용한다.
기존 다른 세션·프로젝트와 전역 설치는 보존하고 main 병합은 나에게 남겨.
첫 구현 후보와 handoff가 준비되면 알려줘. 그때 변경·인계 실험을 진행할 거야.
```

Coordinator는 부모 Issue 하나와 A/B Issue를 만든다. 부모에는 R1 문제지, 공통 규칙, 소유권과 현재 결정 참조를 둔다. 각 기능 Issue는 부모를 참조한다. 실험 결과도 이 부모 Issue 한 곳에서 요약하고, 세부 구현·검증은 각 PR에 둔다.

공용 입력 검증·상태 판정·명령 진입점은 A 또는 B 중 지정한 소유자의 구현자가 먼저 준비한다. Coordinator는 소유자를 기록하고 그 commit을 A/B의 공통 기준으로 전달한 뒤 별도 Herdr Feature Leader와 worktree에서 병렬로 진행한다. 공통 작업용 세 번째 기능 세션은 필요 없다. 예를 들어 `model.py`, `io.py`, `__main__.py`, 공용 tests·README·sample은 한 소유자가 맡고, `listing.py`와 그 tests는 A, `summary.py`와 그 tests는 B가 맡을 수 있다. 파일명은 예시이며 중복 작성 방지가 조건이다.

실제 모델 설정을 임의로 바꾸지 않는다. 구현·독립 리뷰 역할과 검증 범위는 설치된 지침을 따른다. 고정적인 추가 reviewer·별도 보고서를 붙이지 않는다. 첫 후보 전까지 사람의 설명 개입, 대기, 충돌과 재작업을 간단히 기록한다.

## 3. 세션 교체와 공통 규칙 변경

1. A/B 첫 후보가 나왔는지 확인한다. B가 R1 기준 후보 SHA, 검증, 남은 일·다음 행동을 자기 Issue에 handoff로 남기게 한다. 아직 B의 최종 PR 완료로 처리하지 않는다.
2. B의 native child 작업이 종료되고 변경이 보존됐는지 확인한 뒤, **실험용 B 실행만** 정상 종료한다. 실제 종료 여부를 조회한다. worktree·commit·Issue·locator는 삭제하지 않는다. `idle` 관찰만으로 종료됐다고 간주하지 않는다.
3. 다음 변경 카드를 부모 Issue의 최신 결정으로 게시한다. R1의 상태 규칙·summary 출력·sample만 대체함을 적고 A/B Issue에 그 원본 링크를 연결한다. B의 이전 handoff는 이력으로 보존한다.

### 변경 카드 R2 — 이 단계에서 공개

```text
요구사항 변경 R2:
외부 응답을 기다리는 작업을 blocked로 구분하자.
blocked는 완료가 아니므로 active 목록과 active 집계에 포함해.
summary에는 blocked 개수도 별도 필드로 추가해. total/active/done 의미는 유지해.

sample에서 t2의 status를 doing → blocked로 바꾸고 다음 작업을 마지막에 추가해:
{"id":"t6","title":"외부 응답 확인","project":"lab","status":"blocked"}

공유 규칙의 최신 원본과 변경 이유를 기록하고 A/B에 전달해.
각 기능은 영향과 반영 계획을 반환하고, 공용 파일은 단일 작성자로 유지해.
R1의 다른 요구와 오류 검증은 그대로 유효해.
```

4. Coordinator가 A의 영향 응답을 받고 B는 교체 후 확인해야 함을 기록하는지 관찰한다. 의존 작업만 대기시키고 독립적인 문서·검증 준비는 진행할 수 있다. 공통 R2 수정은 기록된 소유자의 구현자에게 직렬 배정하고, 정확한 공유 commit을 양쪽에 전달한다. B가 소유자라면 아래 교체·인수를 마친 뒤 수정한다.
5. 기존 B 실행이 실제로 없는지 확인한 후 새 B Feature Leader를 시작한다. 이전 채팅은 복사하지 않는다. 다음 최소 프롬프트만 주고 원본 탐색과 첫 올바른 행동까지 시간을 잰다.

```text
<B Issue 실제 URL>의 남은 일을 이어서 완료해 줘.
작업 위치는 <보존된 branch/worktree 실제 경로>야.
이전 실행은 종료됐고 기존 변경은 보존돼 있어. 현재 기록을 확인하고 이어서 진행해.
```

6. B가 부모 Issue의 R2와 낡은 handoff를 대조하고, R2 반영 또는 비영향 근거를 반환하는지 확인한다. 이전 후보·리뷰의 유효 범위는 재사용하되 달라진 동작의 검증은 갱신한다. 정확한 새 실행 위치로 실험 B binding을 갱신한다. 기존 working 세션을 중복 시작하지 않는다.

R1에서 `blocked`를 오류로 보던 테스트를 R2에 맞춰 바꾸는 것은 정당한 요구 변경이다. `mystery` 같은 정의되지 않은 상태의 거절, 중복 ID·입력 불변 등 변하지 않은 조건을 지우면 실패다.

## 4. 최종 기능 판정과 PR 연결

진행자는 R2 sample을 사용해 다음 결과를 직접 확인한다. 구현자의 테스트 통과 보고만으로 표의 판정을 대신하지 않는다.

| 명령/입력 | 기대 결과 |
|---|---|
| `list --input data/sample.json --active` | ID 순서 `t1, t2, t4, t6`; `t2`, `t6`의 원래 `blocked` 값 보존 |
| `list --input data/sample.json --project lab --active` | `t4, t6` |
| `summary --input data/sample.json` | `{"total":6,"active":4,"done":2,"blocked":2}` |
| `summary --input data/sample.json --project home` | `{"total":3,"active":2,"done":1,"blocked":1}` |
| 빈 배열 또는 없는 프로젝트 | list는 `[]`, summary는 네 count 모두 0 |
| 다른 임시 입력의 `mystery` 상태, 중복 ID, 깨진 JSON | 각각 exit 1, stdout 비어 있음, 원인 설명 |
| 실행 전/후 입력 파일 | bytes 동일 |

명령 앞에는 `python -m tasklens`를 붙인다. 잘못된 입력은 별도 임시 파일로 만들고 sample을 훼손하지 않는다. 독립 리뷰의 후보 SHA와 최종 통합 SHA를 기록하고, 두 기능을 포함한 통합 branch에서 `python -m unittest discover -s tests -v`를 한 번 실행한다. 제품 변경·통합 충돌 수정은 구현자에게 배정한다. 각 PR과 최종 통합에서 달라진 부분만 추가 검토한다.

A/B PR은 GitHub가 관련 Issue로 인식하도록 연결한다. 실제 기본 branch를 대상으로 한 `Closes #번호` 등 GitHub의 관계를 확인하고, 단순 본문 링크를 관계 조회 성공으로 세지 않는다. 사람이 병합하기 전에는 병합 완료로 표시하지 않는다. PR 생성 직후 관계가 아직 없으면 관찰 결과와 재확인 시점을 기록한다.

실제 Windows Monitor에서 A/B Issue와 PR을 번갈아 선택한다. PR에서 해당 Issue의 기능 세션이 보이고 `작업 정보 복사`의 위치·링크가 화면과 일치하는지 확인한다. 다른 프로젝트로 이동했다 돌아온 뒤 B의 최신 실행이나 handoff로 재개할 수 있어야 한다. 다른 프로젝트가 없으면 그 전환 항목은 미검증이다.

Projects를 쓰는 환경에서는 저장소 지정 보기와 Projects-only 보기를 각각 확인한다. GHES는 실제 해당 host에서 별도 기록한다. github.com 성공을 GHES 성공으로 확대하지 않는다. 현재 PR 상세 TTL은 60초이며 실패도 캐시한다. 그 안의 수동 새로고침으로 즉시 재조회가 보장된다고 판정하지 않는다.

실제 화면을 열어 확인한 이미지와 조작 결과를 남긴다. 브라우저 fixture, native Wails, CLI 결과를 구분한다. 화면/실행 도구가 없으면 가능한 코드 결과는 보존하고 해당 항목은 미검증으로 남긴다.

## 5. 조회 실패와 locator — 환경이 준비됐을 때만

이 단계는 정상 협업 실험과 별도로 판정한다. 확인하지 못한 하위 항목을 성공으로 합산하지 않는다.

**안전한 설정 오류 확인:** 현재 Monitor는 OS 사용자별 설정 파일 하나를 사용하며 저장 시 전체를 다시 쓴다. 앱에 실험용 profile 전환 기능이 있다고 가정하지 않는다. 이미 승인된 별도 시험 Windows 사용자/프로필 등으로 **실제 설정 경로가 운영 사용자와 분리됐고 운영 대상이 없으며 다른 설정 작성자도 없는 것**을 확인·기록한 경우에만 진행한다. 격리 근거가 없으면 이 항목은 미검증으로 남기고 운영 사용자의 설정을 수정·복원하지 않는다. 시험 사용자 생성이나 OS 설정 변경은 이 문서만으로 실행하지 않는다.

격리된 시험 설정을 저장한 뒤 GitHub 대상에 존재하지 않는 시험 저장소를 지정해 Herdr 관찰이 유지되는지 확인하고 즉시 복원한다. 이어 연결 파일 경로만 존재하지 않는 시험 경로로 바꿔 GitHub 관찰이 유지되는지 확인하고 복원한다. 같은 시각의 각 source 결과를 기록한다. 공유 WSL 배포판 전체를 끄거나 인증을 삭제하지 않는다. 이 검사는 설정/조회 오류 격리이며, 동일 설정에서의 cached/stale 복구 성공 증거가 아니다.

**동일 설정의 native 실패·복구:** #43의 cache/stale 완료 판정에는 정상 관찰을 얻은 같은 앱·설정·source key를 유지한 채 GitHub 조회 실패와 Herdr 조회 실패를 각각 재현해야 한다. 진행자는 설치된 환경에서 가능한 실험 전용 실패 방법, 대상·영향·복원 절차를 먼저 기록한다. 기존 도구가 제공하지 않는 fault-injection 옵션을 가정하거나 제품에 실험용 우회 경로를 추가하지 않는다. 안전한 방법이 없으면 이 항목은 미검증이다. 실패 시 마지막 성공 관찰 시각과 stale/error 표시, 다른 source의 새 관찰, 복구 후 실제 재조회까지 확인한다. 설정 변경·앱 재시작으로 캐시를 지운 결과와 구분한다.

**locator 동시 갱신:** 승인된 시험 binding 두 개를 같은 실제 user-level locator에서 서로 다른 Agent가 갱신한다. 둘 다 갱신 요청을 시작한 뒤 최종 값이 모두 남는지 확인한다. lock 내부 재조회→자기 exact binding 변경→temporary file/atomic rename 근거를 남긴다. 충돌이 없었던 한 번의 성공만으로 모든 경쟁 상태를 보장한다고 주장하지 않는다. 다른 프로젝트 binding은 변경 전후 의미상 동일해야 한다. 없으면 프로젝트 간 보존은 미검증이다.

**locator 정리:** 아래 네 경우를 실험용 binding에서 관찰한다. 사용 중인 실제 업무의 Issue/PR/세션을 이 조건에 맞추려고 변경하지 않는다. 실제 상태 조합을 만들 수 없으면 임시 사본의 연습으로만 기록한다.

| Issue closed | PR 작업 finished·남은 handoff 없음 | top-level 실행 absent 확인 | 기대 |
|---|---|---|---|
| 아니오 | 예 | 예 | 보존 |
| 예 | 아니오 | 예 | 보존 |
| 예 | 예 | 아니오 | 보존 |
| 예 | 예 | 예 | 해당 feature binding만 제거 |

실험 PR은 결과 보존 후 사람이 종료할 수 있다. 실제 merged/closed 상태와 남은 작업을 확인하며 `idle`, `done`, 조회 실패를 absent로 바꾸어 세지 않는다. 정리 후 worktree·사용자 파일·다른 binding은 보존한다. 복원도 lock 아래 자기 binding만 대상으로 하며, 과거 locator 전체 백업으로 다른 Agent의 최신 변경을 덮어쓰지 않는다.

## 6. 판정과 개선 선택

[기록 양식](harness-pilot-record.md)의 각 행을 **통과 / 실패 / 미검증**으로 채운다. 전체 점수로 합치지 않는다. 실패는 실제 어긋난 행동, 미검증은 환경·권한·증거 부족이다. 별도로 관찰된 결함은 미검증 속에 숨기지 않는다.

- 기능·협업 통과: A/B 최종 동작과 원 수용 조건, 독립 리뷰·통합 검사, R2 전파, B의 재개를 모두 확인했다.
- native 운영 통과: 실제 앱의 관계·복사·전환과 각 실패/복구 경로를 확인했다. CLI/브라우저 성공으로 대체하지 않는다.
- 정리 통과: 실제 상태 조합·잠금 경합·다른 binding 보존을 확인했다. 임시 사본의 성공은 별도 수준이다.

핵심 지표는 낡은 결정으로 생긴 재작업 건수, 재개에 필요한 추가 설명 횟수와 소요 시간, 충돌·통합 수정량, 사람의 조정 시간이다. 계획된 R2 요청·B 교체 지시는 구조상 필요한 개입으로 따로 기록하고 ‘불필요한 재설명’에 포함하지 않는다. 모델 비용이 실제 제공되지 않으면 추산치를 실제 비용처럼 기록하지 않는다.

한 번의 병렬 실험만으로 순차 방식보다 빠르다고 결론내리지 않는다. 첫 실험은 결함·불편을 찾는 데 사용한다. 같은 원본을 반복해서 찾느라 재개가 지연됐다면 그때 최근 결정/handoff의 작은 조회 기능을 검토한다. 중복 보고·검증이 시간 대부분을 차지하면 해당 절차부터 줄인다. 추가 자동화는 관찰된 문제와 연결해 최대 1~2개만 제안한다.

결과는 부모 Issue와 PR에 연결하고 제품 Issues [#43](https://github.com/Middleages/thread-dock/issues/43), [#48](https://github.com/Middleages/thread-dock/issues/48), [#91](https://github.com/Middleages/thread-dock/issues/91)의 **해당 조건에만** 근거로 사용한다. 이 실험은 #91의 Toolbox migration·native 전 범위를 검증하지 않으며 해당 Issue를 일괄 종료하지 않는다.
