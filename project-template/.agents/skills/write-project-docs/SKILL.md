# Write project docs

Write for the named audience and purpose. Use repository sources and the task packet as the evidence boundary; preserve decisions, commands, links, and caveats rather than smoothing away uncertainty. Organize the result so the reader can find the purpose, decision or current state, supporting evidence, and next action when those facts apply.

## Editorial boundary

Prefer the existing document and its local terminology. Add structure when it helps a reader find an answer, but do not turn a short guide into a mandatory form or duplicate a source of truth. Keep examples and commands executable as written, and label historical or environment-specific evidence instead of presenting it as current behavior.

Keep one source of truth and avoid adding a second checklist or status system. Make only the assigned documentation edits, inspect the final diff, and report any fact or link that remains unverified. Do not publish to GitHub or delegate additional work.
