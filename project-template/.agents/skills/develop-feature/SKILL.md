# Develop feature

Own one feature and its plan through reviewed PR readiness. GitHub is the durable record; native children work inside the Feature Leader's Herdr session. For Herdr CLI operations, first use `herdr-local`.

1. **Intake or resume.** Read the source request, original acceptance, repository guidance, current GitHub decisions/handoff, dependencies and [shared development stance](references/development-stance.md). Reconcile their revisions with the supplied plan and candidate; reuse unchanged decisions and valid review/check evidence. Own technical choices and record reasons. Route cross-feature contracts to the Coordinator and only undelegated product changes to the user. Acknowledge a changed shared contract with its reference and your plan/task adjustment or evidence of no impact before dependent work resumes; continue unrelated authorized work.
2. **Plan proportionally.** A small clear task needs a short approach. Explore genuinely unresolved substantial design choices with `brainstorm-design`; for UI work use [UI quality](references/ui-quality.md), reusing any comparison that answers the same question. Significant new plans or materially changed risk require `grill-plan`: fixed revision, one fresh independent plan reviewer and owner resolution, with a separate adjudicator only for a remaining material disagreement. Planning-only work stops after applicable review/resolution, before implementation or publication. An explicit ideas/draft request may return an `unreviewed draft` with open items.
3. **Split and dispatch.** Prefer a narrow, verifiable end-to-end slice, with actual prerequisites explicit. Agree shared interfaces before parallel writes. Every product-code/test edit, including review and conflict fixes, goes to a bounded native implementation child; a single task uses one child. Parallelize only independent writers in isolated worktrees, within the repository worker budget. Small documentation-only corrections may be handled directly by the owner; helpers are optional.
4. **Give a compact packet.** Include source/acceptance and edge-case meaning, owned scope and exact write location/base revision, relevant dependencies/contracts, and required verification/result evidence. Reference already-known values; omit inapplicable fields. Use `td_implementer` + `tdd-task`, `td_reviewer` + the requested review mode, and only when useful `td_explorer` + `explore-codebase` or `td_docs_editor` + `write-project-docs`. Use native `task` on OpenCode or the harness equivalent. If a named leaf is absent, use an existing allowed native agent with the same Skill/scope. If dispatch is unavailable or denied, report the affected work pending; do not substitute primary-session implementation, models or permissions.
5. **Integrate and verify.** Use `agent-wait` while native work/review is outstanding. Integrate returned changes and run affected focused checks; reserve a required full gate for final integration. Obtain the rendered/interaction evidence required by UI quality. Preserve candidate SHA, commands, environment, outcomes and missing checks; reuse trustworthy identical evidence.
6. **Review once per candidate/scope.** Use `review-change` in a fresh implementation-independent context against the exact candidate and original acceptance evidence. Reuse an existing valid review of that same SHA/scope. Return missing acceptance or blocking findings as the smallest bounded fix/check; code/test fixes go to an implementation child, followed by new-SHA review. Replan after the same root cause repeats twice.
7. **Publish.** Use `publish-work` for the current evidence record, handoff and relevant Project/docs/locator updates within authorization. Human main merge remains final.

Children return to their parent; they are not new Herdr top-level bindings. For plans that require `grill-plan`, record its revision, actual reviewer result/verdict, remaining material items and implementation readiness in the existing response/handoff. A reviewed plan can still lack a decision, fact, dependency or authorization needed to implement. Small clear work needs no artificial plan-review receipt or new status store.
