# Develop feature

Own one feature from accepted scope to reviewed PR readiness. GitHub is the durable record; the Feature Leader coordinates native subagents inside one Herdr top-level session.

For Herdr CLI operations, use **REQUIRED SUB-SKILL:** `herdr-local` for installed syntax, managed context, actual target identity, and any explicit network constraints. Existing authorization carries forward; report only a concrete missing prerequisite for the affected operation.

1. Read the Issue, original acceptance criteria, repository instructions, dependencies, shared-interface warnings, and [shared development stance](references/development-stance.md). When assigned by a Coordinator, read the overall plan reference/revision and applicable decisions/contracts in the feature packet. Reuse its reviewed decisions and expand only this feature into concrete files, tasks, and tests. Pass the relevant criteria and original behavior/edge-case meaning to implementers and reviewers from the start. Return proposed cross-feature contract, boundary, dependency, or overall-assumption changes to the Coordinator for affected-scope replanning; continue independent authorized work. A planning-only assignment ends with the detailed plan and does not authorize implementation or publication.
2. For a substantial, novel, or architecture-affecting change where multiple viable designs may exist, use `brainstorm-design` to explore and converge on a direction. Skip it for small, well-specified work. For any rendered UI change, read [UI quality](references/ui-quality.md): material copy/design work uses independent perspectives, and every UI change needs rendered visual inspection plus its relevant interaction flow. Reuse the UI candidate comparison as brainstorming input when it answers the same design question.
3. Use `grill-plan` for significant plans (cross-interface/state changes, migrations, or consequential uncertain assumptions), even when the requested outcome is clear, after any needed brainstorming. Skip its multi-agent planning cycle for small, well-specified work.
4. Route every product-code or test edit through a native implementation child, including fixes requested after review. For one small task, dispatch one child. Split multiple tasks only when they can write independently; give each an isolated worktree and use 1-3 children when that helps, without filling capacity for its own sake. For each task, preserve the source Issue/request link, original acceptance criteria, and edge-case output or failure meaning. Include only its bounded owned paths, feature worktree/branch, dependency inputs, and shared-interface warnings.
5. Dispatch each packet with the matching Skill and named native leaf when the harness supports it: `td_explorer` with `explore-codebase`, `td_docs_editor` with `write-project-docs`, `td_implementer` with `tdd-task`, and `td_reviewer` with `review-change`. On OpenCode, invoke its native `task` tool; on other harnesses, use the equivalent native dispatch mechanism. If a harness has no named leaf, pass that same Skill, packet, and bounded scope to an allowed native agent; do not reinterpret the request, bypass a permission denial, add a fallback model, or turn a helper into a top-level session. If no allowed native implementation task is available or permission is denied, preserve the task as pending and report the exact cause; never implement it in the Feature Leader session. Use exploration or documentation helpers only when the feature needs them; this is not a fixed pipeline.
6. While delegated native work is still outstanding, use **REQUIRED SUB-SKILL:** `agent-wait`. Wake periodically only to collect owned results or blockers; do not busy-poll, rerun checks, or create status churn to keep the parent active.
7. Integrate returned changes in the feature worktree and run only affected focused verification. For UI changes, obtain the visual and interaction evidence defined in UI quality; include concrete observations, not just screenshot paths. Preserve exact commands, outcomes, and candidate SHA.
8. Dispatch a fresh implementation-independent reviewer with **REQUIRED SUB-SKILL:** `review-change` against the exact candidate SHA/diff and acceptance evidence. Use `agent-wait` while that review is outstanding.
9. If review blocks, assign the smallest bounded fix to a native implementation child with `tdd-task` and re-review the new SHA. If the same root cause repeats twice, replan instead of blindly retrying.
10. When ready, use **REQUIRED SUB-SKILL:** `publish-work` for PR, Issue handoff, Project fields, durable docs when warranted, and locator reconciliation.

Internal planner, implementer, reviewer, and publish/docs helpers are transient native subagents. Do not store them as ThreadDock top-level bindings. Worker full-suite runs are not the default; reserve the repository-wide gate for final integration when required. Human merge remains final.
