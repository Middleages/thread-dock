# Repository rules

- Change only the assigned paths and keep unrelated dirty work intact.
- Apply the shared development stance reference in the installed `develop-feature` skill from planning through review. Significant new or materially changed feature plans use one independent adversary and owner resolution; a different neutral adjudicator is only for a remaining material disagreement. Small bounded work stays lightweight. UI changes use `develop-feature`'s UI quality reference for independent material copy/design proposals and actual rendered visual plus interaction verification. Finish with `publish-work`'s user-facing explanation and truthful evidence limits.
- Use GitHub Issues, Projects, PRs, and Wiki as the durable project record.
- The Coordinator uses `coordinate-work` to distinguish product ambiguity from factual unknowns, implementation choices, and reversible assumptions, then hands off a brief. Each Feature Leader owns its feature plan and reuses an already-agreed plan after intake/feasibility checks. Preserve planning-only scope, active sessions, and independent authorized work; coordinate cross-feature contracts/dependencies narrowly and return undelegated product changes to the user.
- A central coordinator routes every independently deliverable feature that needs implementation to a top-level Herdr Feature Leader session. Each Feature Leader owns the plan, dispatch, integration, focused checks, review handoff, and durable records; every product-code or test edit, including review fixes, is written by a bounded native implementation child with `tdd-task`. A single small task uses one child; independent tasks may use separate worktrees and run in parallel when useful.
- If a native implementation or review task is unavailable or denied, preserve the work as pending and report the exact cause. Do not fall back to the primary session, override permissions, or substitute a model. Named leaf agents are preferred when the harness provides them; otherwise use an existing allowed native agent with the same Skill and bounded scope.
- Record rationale, acceptance criteria, decisions, handoffs, checks, review results, blockers, and links in GitHub. Discover every relevant Project membership for the Issue/request, read each board's options, and keep status, priority, and waiting fields aligned per board. Keep unavailable-board failures distinct and continue the Issue/PR flow.
- Use native `gh` or connected GitHub MCP tools with existing authorization. Query actual IDs and field options; do not invent external identifiers.
- Do not require Go orchestration, Contract v2, Invocation or Artifact envelopes, publisher/repair services, a monitor, or `.threaddock/sessions.json` to begin work.
- Keep session/worktree/pane associations as explicit locators when available. Preserve every worktree; an operator decides any forced deletion.
- Never claim checks, writes, reviews, or completion without evidence for the exact commit. Humans perform the final merge into `main`.
