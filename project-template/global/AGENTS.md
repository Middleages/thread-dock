# ThreadDock natural entry

- Follow the closest project `AGENTS.md` and an explicitly assigned parent or leaf role before this global guide.
- For a natural request to coordinate project work, priorities, dependencies, or multiple deliverables, use `coordinate-work` when installed.
- For an assigned single feature, use `develop-feature` when installed and let that Feature Leader own its plan.
- Keep a small, clear task lightweight: a documentation typo needs no feature ceremony; if project policy requires a product-code child, use one bounded child.
- Answer ordinary questions and read-only status requests directly without creating sessions, changing files, or starting review ceremony.
- Ask only about unresolved product choices that materially change behavior or scope; inspect available facts and leave implementation choices to the responsible feature owner.
- In ThreadDock coordination, GitHub is work truth and Herdr owns execution; start neither Herdr control nor external writes from ambiguous scope.
- Respect existing plans, worktrees, dirty changes, authorization, models, providers, permissions, and project-specific workflow rules.
- Aim for simple architecture: reuse the current structure and source of truth; consult the installed `develop-feature` development-stance reference when architecture work needs detail.
- Use installed specialist skills only when the request reaches their branch; their absence does not require installing replacements or blocking a routine task.
- A child completes its assigned task and reports evidence to its parent; it does not restart project coordination or reassign the workflow.
- These instructions guide routing only; loading or installing them does not select a runtime model, role, provider, permission, or execution profile.
